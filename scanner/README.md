# Сканер архива: алгоритм и границы текущей версии

Обновлено 8 ноября 2026 года. Программа и окно — **1.2.0**, формат задания — 1.0.0,
правила выборки — **v2**. Изменения логики вносить одновременно в код, этот файл,
[`PORTABLE.md`](PORTABLE.md) и тесты. Решения сессий — в [`../docs/`](../docs/).

Основной путь сканирования — **переносной сканер** (`portable.py` + `gui.ps1`), на любом
Windows 10/11 x64. Инструкция пользователя — [`PORTABLE.md`](PORTABLE.md).

## Этап 1 — идентификация и опись (реализован)

1. **Регистрация.** При новом сканировании Windows сообщает серийный номер и ёмкость
   устройства, модель; по тому — серийный номер, ёмкость, метку и файловую систему.
   Это `record` в `job.json` — по нему диск ищется при каждом запуске. Дополнительно
   сохраняется полное описание (`identity_at_registration`): шина, HDD/SSD,
   состояние, прошивка, разметка, GUID раздела и диска или подпись MBR, путь тома,
   буква, компьютер. Без аппаратного серийного номера сканирование не начинается.
2. **Поиск диска при каждом запуске.** Среди подключённых дисков ищется ровно одно
   совпадение по серийному номеру и ёмкости устройства, затем по серийному номеру и
   ёмкости тома. Буква — только текущий адрес. Нет совпадения или их несколько —
   остановка. Смена USB-моста может изменить серийный номер: чинить вручную, не по букве.
3. **Обход.** Пропускаются `$RECYCLE.BIN`, `System Volume Information`, `RECYCLER`,
   `.Trashes`, `.fseventsd`, `node_modules`, `.git`, `.svn`, `__pycache__`, `.venv`,
   `venv`, `$Windows.~BT`; ссылки и все reparse points; имена `.env`, `.env.*`, `*.env`
   (до обращения к метаданным). Содержимое файлов не открывается.
4. **Сохраняется** для каждого файла: относительный путь, размер, даты (текстом —
   значения Windows не помещаются в INTEGER SQLite), file ID, атрибуты, категория
   (медиа ≥ 1 МиБ, медиа < 1 МиБ, сопроводительные, прочие — категории описи,
   не путать с правилами выборки).
5. **Контроль тома** перед каждым каталогом; недоступные пути — в таблицу `errors`.
6. **Итоги:** количество и объём по категориям, расширениям и верхним папкам;
   статусы `complete`, `complete_with_errors`, `interrupted`.

Прерванная опись повторяется заново; незавершённая база переименовывается, готовые
хеши не трогаются.

## Этап 2 — SHA-256 (реализован)

**Правила выборки v2** (`build_selection.THRESHOLDS_V2`): медиа из общего списка
расширений, вне служебных папок; JPEG/HEIC от 50 000 байт; видео любого ненулевого
размера; прочие изображения и RAW от 150 000 байт. **v1** — все медиа от 1 МиБ;
сохранены байт в байт для распознавания старых заданий.

Алгоритм (`portable.process`, `hash_files.hash_one`):

1. Файлы выборки обрабатываются от мелких к крупным.
2. Готовый хеш используется повторно, только если размер, дата изменения и file ID
   совпадают с описью и с текущим файлом (file ID = 0 в старых описях — «неизвестен»).
3. Иначе: проверка reparse points во всём пути, сверка метаданных, чтение блоками по
   4 МиБ, повторная сверка открытого файла, пути и тома после чтения.
4. Каждый хеш сохраняется отдельной транзакцией. Первая ошибка чтения останавливает
   проход и записывается в базу и `log.txt`.
5. Итог — в `result.json`; статус `complete_with_inventory_errors` означает, что часть
   папок была недоступна при описи.

**Добор (v1 → v2).** При продолжении задания v1 правила переводятся на v2 до начала
чтения (запись в `job.json → policy_history`, `runs.jsonl`, `log.txt`). Поскольку
v2 включает всё, что выбирала v1, все старые хеши используются повторно, а читаются
только новые мелкие файлы. Старые программы затем отказываются продолжать задание.

**Прогресс и прогноз.** Каждые 2 секунды рабочий процесс атомарно пишет
`--progress-file` (этап, процент, объём, файлы, скорость, остаток, прошедшее время).
Скорость — за скользящее окно 10 минут; из остатка исключены файлы, хеш которых,
вероятно, будет переиспользован. Читаемая строка — каждые 10 секунд в окно и раз в
минуту в `log.txt`.

**Сон и остановка.** На время работы автоматический сон запрещается
(`SetThreadExecutionState`). Кнопка остановки создаёт файл-сигнал; он проверяется
между каталогами, файлами и блоками. Прерванный файл читается заново.

Хеш не доказывает исправность фото/видео и не диагностирует поверхность диска.
Встроенные EXIF входят в байты файла: изменение EXIF меняет хеш. Похожие, но не
идентичные кадры этот этап не ищет.

## Результаты и перенос (реализованы)

- Новое задание создаётся в `<папка результатов>\<HDDxx - модель - ёмкость - метка>\<HDDxx_код>`;
  папка уже известного диска используется повторно.
- После каждого сканирования и импорта пересоздаётся «Реестр дисков» (.md и .csv,
  разделитель «;», UTF-8 с BOM для Excel) с предупреждениями о конфликтах номеров и
  заданиях по старым правилам. Папки на «_» в реестр не входят.
- `export` / `export-all`: только завершённые задания; копии сверяются по SHA-256,
  создаётся `checksums.json`.
- `import`: одно задание или папка с несколькими; проверка контрольных сумм; код
  задания — исходный; повтор без изменений ничего не делает; более новая версия
  (больше хешей) заменяет прежнюю с переносом в `_Архив\Заменённые задания`; более
  старая отклоняется. Импорт принимает экспорты 1.0.x.
- `index <папка>` — пересоздать реестр вручную.

## Этап 3 — не реализован: общий каталог и план

Группировка по размеру и полному SHA-256 по всем дискам; уникальное содержимое и
физические экземпляры; даты съёмки (EXIF/QuickTime с учётом UTC/местного времени,
источника даты и ручного исправления); события и годы; стоимость освобождения дисков
(см. правило освобождения в `../docs/SESSION_2026-11-08.md`). Отчёт без исполнения
операций. Старые `index_G/S/D/E/F.txt` не связывать с номерами без доказательства
происхождения.

### Сопроводительные и остальные файлы

Правило пользователя от 7 ноября 2026 года, также в `sorting_rules.json`:

- Файлы любых расширений в папке с фото/видео остаются с ними: DOC, PDF, презентации,
  описания, программы поездок. Расширение не определяет ценность.
- Подпапки внутри подтверждённой папки поездки/события остаются с событием, даже если
  в них только документы. Границы события сначала предлагаются в отчёте; общий
  родитель с медиа не делает соседние папки одним событием.
- Несвязанные файлы и папки — в план переноса в
  `НЕ ФОТО и НЕ ВИДЕО\HDDxx\исходный относительный путь` для ручного разбора; без
  плоского списка и без перезаписи одноимённых файлов. При неопределённости — на месте.
- Наличие медиа определяется с учётом мелких фото/видео, а не только выборки SHA-256.
- Служебные папки, секреты, ссылки и reparse points в общий разбор не переносятся.

Примеры: `Алтай 2021/Программа.pdf` остаётся с фото; `Алтай 2021/Документы/Описание.docx`
остаётся в событии; отдельная папка `Книжки/*.zip` — в ручной разбор.

## Этап 4 — не реализован: копирование и отдельное удаление

Только после проверки отчёта и утверждения плана. Копирование во временное имя с
расчётом хеша при чтении источника → перечитывание назначения и сверка → завершение
имени → запись в журнал. Одноимённые разные файлы не перезаписываются. Удаление —
отдельная операция и только когда каждый экземпляр после свежей проверки есть ещё в
двух местах на разных физических дисках. Карантин на том же диске места не
освобождает. Тесты: нехватка места, отключение носителя, прерванная запись, повторное
исполнение, ошибка проверки.

## Исторический локальный путь (HDD01/HDD02, 07.11.2026)

`inventory.py --disk HDDxx` и `hash_files.py --selection …` работали с реестром
`disks.json` и папкой `../Каталог дисков/`. Их результаты переведены в формат задания
и лежат в `СКАНИРОВАНИЕ ДИСКОВ`; исходники — в `СКАНИРОВАНИЕ ДИСКОВ\_Архив`. Для новых
дисков этот путь не использовать.
