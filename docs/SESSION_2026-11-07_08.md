## 1. Исходная задача

У пользователя больше 16 физических дисков разной ёмкости, сотни тысяч фото и
видео. Архивы частично пересекаются: одинаковые файлы встречаются на разных
носителях под разными именами, а разные файлы могут иметь одинаковые имена.
По исходной оценке пользователя, копии занимают более трети суммарного объёма;
эта оценка ещё не подтверждена новым сравнением хешей.

Нужно получить единый каталог, установить точные копии по содержимому, сохранить
контекст поездок и событий, затем подготовить управляемую перегруппировку.
Потеря единственного экземпляра недопустима. Количество сохраняемых независимых
копий для разных категорий пока не согласовано: найденный дубль не равен лишней
резервной копии.

## 2. Что было изучено и какие решения выбраны

| Вопрос | Решение | Статус |
|---|---|---|
| Старые индексы и отчёты | Сохранить как исторические данные, не выдавать сравнение имён/размеров за сравнение содержимого | Аудит сохранён локально в `Анализ/` |
| Готовые приложения | Обсуждались WinCatalog, AllDup/Czkawka, FreeFileSync, Auslogics; материалы исследования лежат в `Источники информации/` | Альтернативы, не зависимости сканера |
| Основа нового анализа | Собственные воспроизводимые Python-скрипты и SQLite | Реализовано |
| Подключение носителей | Обсуждались SATA, USB ACASIS, док-станции и Hot Swap-корзины | Сканер не привязан к конкретной модели; покупки и их результаты здесь не подтверждаются |
| Ускорение | Распределить чтение содержимого между тремя компьютерами | Пользователь подтвердил два дополнительных Windows 10 x64 |
| Передача | Переносной комплект и результаты через флешку | Реализованы экспорт и импорт |

| Управление исходниками | Регулярная работа с Git CLI, репозиторий `wadimka78/hdd-opimization-foto-video` | При документировании обнаружен коммит d8590e0; локальная ссылка origin/main указывает на него |

Установка Python на дополнительные компьютеры не требуется: комплект содержит
официальный Windows x64 embeddable Python 3.13.17. Сторонних Python-пакетов в
современном сканере нет. Сборщик сверяет SHA-256 скачанного архива Python.
После сборки переносной сканер работает без интернета. Скиллы, Codex и субагенты
на рабочих компьютерах не нужны.

## 3. Идентификация: номер носителя не равен букве Windows

Принята постоянная нумерация: HDD01 — исходный диск на 2 ТБ; HDD02 — WD My
Passport на 500 ГБ. Буквы G/H были адресами во время первых проходов, а не
постоянными идентификаторами. Буквы из старых отчётов нельзя автоматически
сопоставлять с нынешними дисками.

Перед чтением проверяются:

1. Аппаратный серийный номер и физическая ёмкость устройства.
2. Среди его подключённых томов — серийный номер тома и размер тома.
3. Должно найтись ровно одно совпадение; иначе остановка для ручного разбора.

Метка тома — подсказка человеку. Windows UniqueId не принят за единственный
постоянный ключ: при работе с HDD01 его значение менялось. После замены USB-моста
может измениться и доступный аппаратный серийный номер. Автоматически исправлять
реестр по одной букве, имени или ёмкости запрещено.

Основной реестр — `scanner/disks.json`; человеческая таблица —
`Каталог дисков/Реестр дисков.md`. Реальные серийные номера не публикуются в Git.
`disks.example.json` содержит только шаблон.

На дополнительных компьютерах новый номер вводится при регистрации задания.
Его обязан заранее назначить пользователь в общем реестре. Автоматического
распределения номеров между компьютерами нет. Отдельный уникальный код задания
не защищает от выдачи одного номера двум разным физическим дискам. При импорте
сопоставление номера с устройством требует проверки на основном компьютере.

## 4. Архитектура

```mermaid
flowchart LR
    A[Архивный HDD] -->|только чтение| B[Windows Forms: выбор диска и папки]
    B --> C[Переносной Python: отдельный процесс]
    C --> D[Локальное задание: каталог, хеши, отчёты]
    D --> E[Экспорт с контрольными суммами]
    E --> F[Флешка]
    F --> G[Импорт с проверкой на основном ПК]
    G --> H[Будущее сравнение и план размещения]
```

Два режима используют общие функции, но разные оболочки:

- Первоначальный локальный режим: `inventory.py` → `build_selection.py` →
  `hash_files.py`. Выборка двух дисков хранится отдельно от баз инвентаризации;
  хеши записываются в общую локальную `hashes.sqlite`.
- Переносной режим: `gui.ps1` запускает `portable.py`. Каждое задание получает
  отдельную папку и базу хешей; одна общая SQLite по сети не открывается.

Интерфейс — Windows Forms в штатном Windows PowerShell. Вычисления выполняет
отдельный Python-процесс. Это позволяет обновлять окно во время чтения HDD.
Результаты по умолчанию — `%LOCALAPPDATA%\HDDScanner\results`, журналы —
`%LOCALAPPDATA%\HDDScanner\logs`. Папку результатов можно выбрать в интерфейсе.
Запись на сканируемый том блокируется. Разные тома одного физического диска
этой проверкой не исключаются: выбирать нужно внутренний диск другого устройства.

## 5. Алгоритм инвентаризации метаданных

1. Установить идентичность носителя и создать папку задания на другом томе.
2. Обойти доступные каталоги без чтения содержимого обычных файлов.
3. Исключить служебные каталоги из `EXCLUDED_DIRS`, например корзину,
   System Volume Information, `.git`, node_modules, виртуальные окружения.
4. Не следовать символическим ссылкам и reparse points. Имена `.env`, `.env.*`
   и с окончанием `.env` исключать до обращения к метаданным.
5. Сохранить относительный путь, размер, даты, file ID, атрибуты и категорию.
   Даты записывать текстом: некоторые значения Windows не помещаются в INTEGER.
6. Перед обходом каталогов проверять том. Недоступные пути записывать в errors.
7. Сохранить сводку и статус: complete, complete_with_errors либо interrupted.

Мелкие файлы перечисляются в метаданных, но их содержимое не читается.
Если проход метаданных прерван, он выполняется заново. В переносном задании
незавершённая база переименовывается, а готовые хеши не удаляются.

## 6. Политика выборки: осознанный компромисс

В старом индексаторе порог 1 МиБ был осознанным ограничением для сокращения
выборки. Недостаток заключался также в узком списке десяти расширений.
Новая версия разделяет дешёвое перечисление метаданных и дорогое чтение содержимого.

Для SHA-256 сейчас отбираются медиа из общего расширенного списка `MEDIA`
размером **не менее 1 МиБ (1 048 576 байт)**. Включены PNG, HEIC/HEIF, TIFF,
многие RAW, M2V, WebM, FLV и другие форматы из кода. Служебные пути исключаются
и при формировании выборки. Все рабочие компьютеры используют одну политику.

Это не хеширование всех файлов диска. Мелкие медиа, DOC/PDF, XMP/AAE и прочие
сопроводительные файлы могут присутствовать в каталоге без хешей. Отдельного
полного прохода их содержимого пока нет. Результат нельзя распространять на них.
Папки не исключаются автоматически по смыслу названий вроде «сайт» или «фильмы».

## 7. Алгоритм полного SHA-256

1. Открыть сохранённую выборку/инвентаризацию; проверить политику переносного задания.
2. Снова найти физический носитель, проверить том. Файлы обрабатывать по размеру
   и пути. Поэтому в конце могут оставаться немногочисленные, но очень крупные видео.
3. Проверить сохранённую запись хеша. Повторно использовать её только при совпадении
   размера, даты изменения и file ID с исходной выборкой и текущим файлом.
   Для старых каталогов file ID = 0 означает «неизвестен», а не иной файл.
4. Если готовой подходящей записи нет, проверить путь и его предков на reparse
   points, проверить размер/дату/file ID, открыть файл и читать блоками по 4 МиБ.
5. Считать SHA-256 всех байтов. После чтения повторно проверить открытый файл,
   путь, размер и идентичность тома.
6. Сохранить успешную запись отдельной транзакцией SQLite. При первой ошибке
   остановиться, записать ошибку и не выдавать хеш неуспешного чтения за подтверждённый.
7. Записать итоговый JSON. Для переносного прохода сохранить также наличие
   ошибок инвентаризации: complete_with_inventory_errors отличается от полного охвата.

Имя и даты файловой системы не входят в SHA-256. Одинаковые байты под разными
именами имеют один хеш. Разные байты при одинаковом имени/размере — разные хеши.
Встроенные EXIF и другие метаданные входят в байты файла: изменение EXIF может
сделать хеш другим, даже если изображение выглядит одинаково. Поиск визуально
похожих фото и перекодированных видео в этой версии не выполняется.

Статус строки `verified` означает успешный расчёт хеша, а не наличие резервной
копии. Кеш не защищает от изменения содержимого с восстановлением прежних метаданных.
Во время прохода нельзя редактировать архив; перед удалением понадобится актуальная
проверка. Хеш не проверяет декодируемость фото/видео и не диагностирует поверхность HDD.

## 8. Остановка, сон и параллельная работа

Хеши завершённых файлов сохраняются. Прерванный файл читается заново с начала;
продолжения с середины видео нет. Проверка кеша требует обхода записей и метаданных,
но не повторного чтения содержимого подходящих файлов. Процент текущего прохода
в начале возобновления не равен проценту утраченной работы.

Переносной сканер препятствует автоматическому сну через SetThreadExecutionState
на время работы и освобождает ограничение при выходе. Ручной сон, закрытие крышки,
отключение USB и сбой питания этим не исключаются.

Кнопка остановки создаёт файл-сигнал. Рабочий процесс проверяет его при обходе,
между файлами и при чтении блоков. Остановка может ждать завершения системного
вызова чтения. Пока процесс работает, окно не разрешает обычное закрытие.

Разные физические HDD можно сканировать параллельно, по процессу на диск;
общий USB-контроллер может ограничивать суммарную скорость. Для одного JOB есть
блокировка файла worker.lock. Два разных JOB одного физического HDD автоматически
не блокируют друг друга: их одновременно запускать нельзя.

## 9. Формат результатов и перенос флешкой

| Файл задания | Назначение |
|---|---|
| job.json | Версия формата/алгоритма, политика, назначенный номер, идентичность устройства, код задания |
| inventory.sqlite | Метаданные, категории, ошибки обхода |
| inventory_summary.json | Итоги инвентаризации и её ограничения |
| hashes.sqlite | Таблица hashes: disk_id, path, size, mtime_ns, file_id, sha256, status, error |
| result.json | Итог последнего прохода, объём выборки, использованные/новые хеши, ошибки, время |
| worker.lock | Защита одного задания от одновременного исполнения |

Экспорт разрешён только для завершённого задания, включая завершение с ошибками
инвентаризации. Берётся блокировка задания, копируются пять файлов результатов,
проверяются хеши исходной и экспортированной копии, создаётся checksums.json.
Исходный локальный результат не удаляется.

Импорт проверяет список файлов и их SHA-256, создаёт отдельную локальную папку
и повторно проверяет скопированные файлы. Проверка целостности не удостоверяет
отправителя. Импорт не перезаписывает реестр, не устраняет конфликты номеров и
не строит группы дубликатов. Эти действия — отдельный следующий этап.

## 10. Интерфейс и исправления этой сессии

Первое консольное меню пользователь отклонил как неудобное. Создано окно:
таблица доступных томов с меткой, моделью, объёмом, свободным местом, типом
HDD/SSD и подключением; выбор папки, подтверждение устройства, продолжение,
остановка, экспорт и импорт. Системные устройства блокируются для нового прохода.
Тип определяется по данным Windows; когда USB-мост его скрывает, выводится
«Не определён». Объёмы интерфейса — ГиБ, объёмы прогресса сканера — десятичные GB.

В первоначальном GUI была серьёзная ошибка проверки: создание элементов окна
проверили, а взаимодействие окна с живым процессом — нет. На втором компьютере
ReadAllText получил отказ из-за открытого файла журнала. Это ошибка интерфейса;
по ней нельзя заключать, что сам сканер остановился. Повторный запуск того же
диска без проверки старого процесса мог создать параллельное задание.

В интерфейсе **1.0.1** чтение заменено на FileStream с совместным доступом
ReadWrite/Delete. Дополнительно сохранён дескриптор рабочего процесса, чтобы
Windows PowerShell корректно получал код его завершения. Добавлен GUI_TEST.cmd:
реальный дочерний процесс пишет живые stdout/stderr, проверяются кириллица,
пробелы и конечная обратная косая черта в пути, успех, ошибка и кнопка остановки.

Версия интерфейса 1.0.1 не меняет версию задания portable 1.0.0: старые JOB
совместимы. Для передачи использовать **HDDScanner-Windows-x64-GUI-1.0.1.zip**.
Сборщик пока оставляет также архив под старым общим именем; это лишняя копия,
а не второй вариант программы. Пользователь справедливо отметил эту путаницу.

сканирования. Последний дополнительный проход пока не объявлялся завершённым.
Во время документирования его не перезапускали и архивные файлы не изменяли.

## 12. Правила будущей перегруппировки

Правила закреплены в `scanner/sorting_rules.json`, но переносы не реализованы.

- DOC/PDF, презентации и любые другие материалы рядом с фото/видео сохраняются
  вместе с событием. Расширение само по себе не определяет, что файл лишний.
- В подтверждённой папке поездки сохраняется всё дерево, включая подпапки
  только с документами. Общий родитель с медиа не делает все соседние папки
  автоматически одним событием.
- Несвязанные прочие файлы предполагается выносить в
  `НЕ ФОТО и НЕ ВИДЕО/HDDxx/исходный относительный путь` для ручного разбора.
- При определении связи учитывать маленькие фото/видео тоже. Неоднозначные
  случаи оставлять на месте и показывать пользователю.
- Разные одноимённые файлы не перезаписывать. Перед исполнением нужен план
  размещения с расчётом свободного места и числа независимых физических копий.

Предложенный, ещё не реализованный алгоритм операций: копирование во временное
имя → завершение записи → полное повторное чтение и проверка хеша назначения →
фиксация в журнале → завершение имени. Удаление исходника — отдельная операция
после подтверждения требуемых копий. Простое «перемещение» до проверки копии
не использовать как базовый способ. Карантин на том же диске место не освобождает.

## 13. Git и ограничения среды

При создании `.git` владельцем оказался CodexSandboxOffline. Настройка песочницы
падала с setup refresh had errors до запуска команд. Пользователь из PowerShell
администратора сохранил ACL и изменил владельца 27 объектов на свою учётную
запись. После этого команды заработали.

Отдельные ограничения сохранились: песочнице запрещена запись в `.git`, а её
учётной записи недоступны GitHub credentials Windows. TLS Schannel давал
SEC_E_NO_CREDENTIALS. Пробная команда с OpenSSL дошла до ошибки авторизации;
глобальные SSL-настройки и проверка сертификатов не отключались.
Политика этого чата запрещает require_escalated. Предоставленный через
request_permissions доступ не устранил фактический запрет записи индекса.

Подготовлен `publish_github.ps1` для обычного PowerShell пользователя: проверка
репозитория и доступа → добавление файлов → проверка исключений → коммит →
обычная отправка без force. При итоговой проверке уже обнаружен коммит
`d8590e0` (Preserve HDD inventory tools and add offline Windows scanning kit):
локальная ветка main и локальная ссылка origin/main совпадают. Это уточняет
прежние сообщения о полностью незафиксированном проекте. Свежая проверка сервера
при документировании не выполнялась. Новые изменения документации ещё не
закоммичены. Из прежних незафиксированных этапов нельзя достоверно восстановить
историю отдельных коммитов.

В Git предназначены исходники, инструкции и обезличенные сводки. Не публикуются
реальный реестр, серийные номера, каталоги путей, базы, индексы, Excel-выгрузки,
журналы ACL и собранный runtime. Файлы `.env` не читаются и не изменяются.

## 14. Что предстоит после документирования

1. Проверить полноту готовых баз HDD01/HDD02 и соответствие выборке без чтения
   содержимого архивов. Зафиксировать ограничения анализа.
2. Сгруппировать успешные записи по размеру и SHA-256, раздельно посчитать
   уникальное содержимое и физические экземпляры, копии внутри/между дисками.
3. Показать распределение по папкам, примеры разных имён и конфликты одинаковых
   имён. Не называть объём всех повторов объёмом, разрешённым к удалению.
4. На небольшой группе событий согласовать способ выбора основных папок,
   сохранения сопроводительных материалов и числа независимых копий.
5. Сформировать проверяемый план без исполнения. Затем отдельно проектировать
   копирование, актуальную проверку, журнал восстановления и удаление.

До этих этапов количества групп, объём освобождаемого места и конкретные
кандидаты на удаление остаются неизвестными. Документирование их не устанавливает.
