# Алгоритм обработки описей — согласованные правила

Живой документ: сюда записываются правила по мере согласования с пользователем.
Этап сейчас — **только описание и проверка на данных**: ничего не копируется,
не перемещается и не удаляется. Общий план консолидации — в
[`SESSION_2026-11-08.md`](SESSION_2026-11-08.md), раздел 3.

## 0. Где лежат результаты сканирования и как назначаются номера

- **Одна сводная папка** для всех компьютеров и флешек:
  `РЕЗУЛЬТАТЫ СКАНИРОВАНИЯ - сводные` в папке проекта (вне Git). Результаты с других
  компьютеров переносятся флешкой и добавляются скриптом
  [`catalog/consolidate.py`](../catalog/consolidate.py): копия с проверкой SHA-256,
  источник не меняется; более полная версия задания заменяет прежнюю (та уходит в
  `_Архив\Заменённые задания`); незавершённые задания не берутся.
- Таблицы строятся только из сводной папки
  ([`catalog/build_pilot.py`](../catalog/build_pilot.py)).
- Номер носителя постоянный. Если один номер по ошибке выдан двум дискам, номер
  меняется у одного из них скриптом [`catalog/rename_disk.py`](../catalog/rename_disk.py).
  08.11.2026: HDD07 остался за WD My Passport 500 ГБ «Films», Seagate ST3640323AS 640 ГБ
  «640 гиг - под формат» получил номер **HDD37**.
- Результаты сканирования лучше писать на диск компьютера, а флешку использовать
  только для переноса.

## 1. Роли дисков

- **G — «копилка» 18 ТБ** (копия 1, финальный упорядоченный архив). Около 70 %
  нужного уже на нём.
- То, что не помещается на G, — на освобождённые HDD по 3 ТБ (их четыре, ещё не
  отсканированы). Роль диска 16 ТБ — решить после сканирования.
- Держим **две копии** каждого нужного файла, собранные на как можно меньшем числе
  дисков. Сначала разгружаются SSD и флешки, особенно съёмка до 2024 года.

## 2. Структура события на копилке (08.11.2026)

Каждое путешествие, поездка или событие — одна папка, внутри по типам:

```
<Событие>\JPEG\     — фото JPEG (и HEIC)
<Событие>\RAW\      — сырые фото
<Событие>\Видео\    — видео
<Событие>\...       — всё прочее лежит в корне папки события
```

Подпапку создаём, только если для неё есть файлы. Нет RAW — нет папки RAW.

Сейчас на G поездка разложена наоборот, сначала по типам:
`JPEG - фото всех лет\2014 год\<Событие>`, `RAW - фото 2000 - 2021\2014\<Событие>`,
`Видео\ВИДЕОИСХОДНИКИ - digital\...\<Событие>`.

**Решение 08.11.2026: G перегруппировать по событиям.** Три ветки одного события
(JPEG, RAW, Видео) сводятся в одну папку события с подпапками по типам. Это
перемещения внутри одного диска — данные не копируются, места не требуется.
Выполняется только на этапе исполнения, по утверждённому плану и с журналом
«было → стало».

Порядок подготовки плана перегруппировки:

1. По описи G найти события в каждой ветке (JPEG, RAW, Видео) и сопоставить их
   по названию; совпадение по содержимому (одни и те же снимки) — подтверждение.
2. Для каждого события — строка плана: откуда (до трёх веток) → куда
   (`<Событие>\JPEG|RAW|Видео`), объём, число файлов.
3. Отдельным списком — на ручное решение: события без пары с похожими названиями,
   события с одинаковым названием в разные годы.
4. **Сборники** («Разное», «В разборку» и подобные — не события): каждый файл в
   них сверяется со всем каталогом — с остальным G и с другими дисками.
   Скорее всего, это в основном дубли. Файл, найденный в папке события, — дубль,
   оригинал в событии. На ручной разбор остаются только файлы, которых больше
   нигде нет. Совпадение с другим сборником дублем не считается: так, «В разборку»
   за 2011, 2012 и 2015 годы лежат одинаковыми копиями в ветках JPEG и RAW.
   Проверка по старому индексу G (08.11.2026): 26 сборников, 88,5 ГБ; 24,8 ГБ (28 %)
   есть в папках событий на G, 1,9 ГБ — только на других дисках, 61,8 ГБ больше
   нигде не найдено (с учётом зеркальных пар сборников уникального меньше).
5. **Видео внутри JPEG-ветки** (например, 17 ГБ у «Кораблика» в
   `JPEG - фото всех лет\2014 год\Кораблик…\Видео`) переносится в папку `Видео`
   своего события — автоматически, без ручного решения.
6. Уровень выше события — **год** (подтверждено 08.11.2026):
   `<Год>\<Событие>\JPEG|RAW|Видео`; событие на стыке лет — по году начала.


## 3. Названия

Если одни и те же снимки лежат в папках с разными названиями, **берём название с G**.
Ручное решение по названию не требуется.

**События внутри года — в хронологическом порядке, дата в начале названия**
(08.11.2026), в формате пользователя: `4-11 января 2018 года - <Название>`.
Даты берутся из названия, где они уже есть, иначе — первая и последняя дата съёмки
из EXIF (проход по заголовкам, раздел 7). Событие через границу месяцев:
`28 января - 3 февраля 2018 года - <Название>`.

Проводник сортирует по имени, сравнивая числа как числа, но названия месяцев — как
буквы. Поэтому `15 января…` встанет после `10 марта…`. Чтобы порядок был
хронологическим, предложен номер месяца впереди: `01. 4-11 января 2018 года - <Название>`
(ждёт подтверждения).

## 4. Статус папки на любом другом носителе

Каждая папка на другом диске сверяется с G целиком (а не с отдельными частями
события) и получает один из статусов:

| Статус | Значение |
|---|---|
| **Есть на 18 ТБ** | Всё содержимое уже на G; указывается, где именно. Это дубль: копия на этом диске — кандидат во вторую копию или лишняя (решает планировщик позже) |
| **Частично: не хватает N ГБ** | Часть файлов на G отсутствует — их нужно будет докопировать в папку события на G |
| **На 18 ТБ нет** | Кандидат в копилку целиком |
| **Сафари / АН — позже** | См. раздел 5, в консолидации не участвует |

Таблица показывает папки «свёрнуто»: если вся папка имеет один статус, она — одна
строка (например, вся поездка «Кораблик - майские 2014» на HDD12 — «есть на 18 ТБ»).
Разворачиваются только папки со смешанным статусом.

## 5. Рабочие проекты: Сафари и АН

- Сафари-Портал, Сафари-эксперт, «Сафари» в любом написании и папки со словом «АН»
  («Оленек - АН», «ПОРТАЛ АН - файлы»…) живут на дисках основного компьютера
  C, D «Видеомонтаж», E «Исходники», F «Монтаж - SN850» (HDD09), V «Монтаж Видео».
  Там они остаются без изменений.
- Позже: с флешек и других дисков уникальное переносится на эти диски, дубли
  удаляются; бэкап этих дисков — на отдельный освобождённый HDD. Дубли удалять
  только после этого бэкапа.
- Определение по слову ненадёжно (книги, «парк Сафари» в семейных фото,
  установщик браузера): окончательный список папок подтверждает пользователь.
- **«Летопись…» — туда же** (09.11.2026): папки с названием «Летопись…» на G не
  переносятся и лежат на том же отдельном диске, что и папки «АН». Найдено:
  `HDD53: Слайдшоу АН Летопись - …` (4 папки, около 495 ГБ),
  `HDD54: САФАРИ\ПОРТАЛ - для АН\ВИДЕООТЧЕТЫ о ПУТЕШЕСТВИЯХ\Летопись, вторая половина 2023 года`
  (и «… - скорректированные», вместе около 44 ГБ), `Flash22: Летопись, вторая половина 2023 года`
  (13,5 ГБ). На G (по старому индексу) таких папок нет. Книги «Летописи …» на HDD02
  и кэш DaVinci на HDD58 к правилу не относятся.

## 6. Мелкие файлы

Уникальные изображения до 50 КБ (часто превью больших фото) — в отдельную папку для
просмотра глазами и ручного отбора, разложенную по исходным папкам.

## 7. Даты

Для планирования — год из названия папки, иначе дата файла (ненадёжно). Дату съёмки
из EXIF читать попутно (заголовки файлов, один раз на уникальное содержимое,
в основном с G), без повторного полного сканирования. Удобнее всего — добавить чтение
даты в сканер до полного скана G.

## 8. Не только фото и видео

Опись сканера охватывает **все файлы** (путь, размер, даты), SHA-256 — только у фото
и видео. Поэтому размер любой папки известен, а точные копии документов, архивов
и программ пока определяются только по имени и размеру — для удаления это не годится.

По 21 заданию (08.11.2026): описано 12 181 ГБ, из них фото и видео 8 908 ГБ,
**прочее — 3,3 ТБ**. Крупнее всего:

- кэш DaVinci Resolve (`DaVinci\CacheClip`): 1 673 ГБ на HDD09 и 498 ГБ на HDD03 —
  программа пересоздаёт его сама; очистка — решение пользователя;
- каталоги Lightroom (45, 24, 17 ГБ) — результат работы над фото, **сохранять**;
- системные файлы Windows, книги, бэкапы сайтов, программы — решение по группам.

Предложено: лист «Крупные папки» в таблице (ждёт ответа).

## 9. Повреждённые носители

Пример — Flash05 (08.11.2026): Windows сообщает «Full Repair Needed», чтение части
файлов висит минутами. Порядок:

1. Остановить сканирование; если окно не закрывается — завершить процесс и вынуть
   носитель. Сохранённые хеши не теряются.
2. Для каталога достаточно прочитанного (у Flash05 — 4 003 из 4 019 файлов).
3. Проверить по каталогу, что есть только на этом носителе (у Flash05 около 3 ГБ:
   «Алтай для Алексея», «Номер 1 2003 год», «Я»), и по решению пользователя
   скопировать читаемое на исправный диск.
4. `chkdsk /f` — только после такой копии: «ремонт» может удалить повреждённые файлы.

В сканере 1.3.2 нужны: предел времени на один файл и отказ от повторного чтения
файлов, уже давших ошибку.

## 9а. Подозрение на повреждение (09.11.2026)

Если у файлов совпадают **имя, размер и дата изменения, а SHA-256 разный**, это
подозрение на повреждение одной из копий. Такие файлы:

- не считаются ни дублем, ни уникальным файлом;
- ни одна копия не удаляется и не заменяется, пока пользователь не решит, какая
  правильная;
- подсказка: если копий три и больше и две совпадают — вероятно, верна копия большинства;
  иначе — просмотр файла.

Список строит [`catalog/find_suspects.py`](../catalog/find_suspects.py) →
`Каталог дисков\Проверка - подозрение на повреждение <дата>.xlsx` (столбец для решения).

Первая проверка по 36 заданиям: **2 595 групп, 8 186 файлов** (в основном JPEG).
В 1 443 группах есть большинство. Группы сосредоточены в парах HDD08 ↔ HDD55
(больше 1 100), Flash22 ↔ HDD54 (больше 900, ещё Flash06 и HDD53), есть 99 групп
внутри HDD14. Такая концентрация похожа на системную причину на одном из носителей
пары, а не на случайные сбои; причину нужно выяснить сравнением нескольких файлов.
Самый крупный случай — `Белая 2004 от Бурейцев\Белая 2.avi` (11,6 ГБ, HDD01 ↔ HDD08).

**Разбор пары Flash22 ↔ HDD54 (09.11.2026, побайтное сравнение 16 пар, только чтение).**
Повреждена **Flash22** (Netac 31 ГБ «Слайдшоу», сейчас буква K:):

- Windows сообщает о томе «Full Repair Needed»;
- копии на HDD54 дают тот же хеш, что при сканировании, а у Flash22 хеш теперь
  другой, чем при её же сканировании: флешка возвращает разные данные в разные дни;
- различия идут блоками по 4 КБ (смещения кратны 4096) — типичная картина
  отказывающей флеш-памяти, а не правки метаданных.

Правило: **если носитель повреждён (Full Repair Needed, нестабильные хеши), его копии
в группе «подозрение» считаются испорченными, верна копия с исправного носителя.**
С Flash22 только 4 файла нигде больше не найдены: фильм «Игра (1997)» .mkv (3,3 ГБ),
«Рыбный рынок2.mp4» (50 МБ), `Договора\2024\01.jpeg` и `02.jpeg`; их содержимое
может быть испорчено. Остальное (938 файлов, 13,8 ГБ — в основном «Летопись»)
есть на HDD54 в исправном виде. Пары HDD08 ↔ HDD55 и прочие ещё не разобраны.

## 10. Чего ещё нет в данных

Полный скан G с хешами (сейчас — старый индекс от мая 2026 по имени и размеру,
медиа от 1 МБ); диски основного компьютера C, D, E, V; четыре HDD по 3 ТБ; 16 ТБ;
HDD08 и HDD06 (сканируются на другом компьютере); остальные флешки и диски.
